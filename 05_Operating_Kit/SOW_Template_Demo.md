## 1. Objective

Turn the approved package into a working Fieldwire project the field can run from — every unit a pinned task, every unit type a verification checklist — plus a written record of everything the package and the field disagree on.

## 2. Deliverables

1. **Task import** — one task per unit, titled with its mark, described with unit facts (type, sheet and revision, dimensions, finish, flags), and pinned from the plan's text layer.
2. **Checklist setup** — one gate checklist per unit type. Release and acceptance are signed by someone other than the person whose work they verify.
3. **Fieldwire Build Brief (FBB)** — a summary line and seven sections: source and scope, counts, discrepancies, held, not pinned, owed by others, deployment steps. Every open item names an owner. Delivered first, so the field can act on it before the build is finished.
4. **Deployment steps and a live onboarding session** — the import runs with the client on the call, one test row before the rest.
5. **QA/QC on the finished import** — counts reconcile, every checklist name matches exactly, pins checked against an overlay before anything imports.

**If the project already has tasks,** the build lands as a new set at the existing pin coordinates. The original tasks are archived, not deleted, so there is a rollback. Task numbers change; that matters only if someone has written one down.

## 3. Optional add-on

**Drawings cross-check — [fee].** The base scope reconciles the package against Fieldwire. This goes one level further: the architect's schedule and plans against the package, to find units that were added or changed after the package was drawn and never made it in. Anything found is pinned and flagged; its checklist follows once a set or ticket exists for it.

## 4. Out of scope

- Fieldwire licenses and seats
- Fabrication, installation, and field verification of built work
- Work inside the client's Fieldwire project without the client live on the call
- Revisions issued after delivery (see Section 8)
- Field adoption and enforcement

## 5. Who owns what

**I own enablement:** the structure, the data, the Build Brief, and the onboarding session.
**The client's leadership owns adoption:** whether the field completes the checklists and keeps the project current.

A Fieldwire project is only as good as the people updating it. Nothing in this scope can make a crew use it.

## 6. Client provides

- The complete approved package, first page to last, with its revision confirmed as current
- The plan sheets exactly as uploaded to Fieldwire
- A Fieldwire plan that supports task export and import during setup and closeout
- One named decider for open items raised in the Build Brief

## 7. Assumptions and acceptance

**Fidelity.** Deliverables are faithful to the package as issued, at the revision printed on the files. They are not warranted against the drawings, field conditions, or later revisions. The client verifies against the approved package before anything is fabricated or installed.

**Acceptance.** The work is accepted when:
- units on the list equal task rows in the import
- every checklist attaches on import
- the test row's pin lands on its mark
- the Build Brief is delivered with every section present

Acceptance is complete [5] business days after the onboarding session unless an issue is raised in writing.
